# Update Itixo models

Use the source checkout. Never edit an installed plugin cache or hand-edit installed agent files. Apply confirmed Codex choices through `itixo:install-agents` only.

1. Honor a user-specified checkout. Otherwise use the current checkout only when it contains `CLAUDE.md`, `base/rules/agents.md`, `base/agents/`, all three provider plugin directories, and `scripts/generate-agents.js`. Verify its Git root and `origin` or `upstream` points to `ITIXO/itixo-marketplace` or a fork the user authorized. Reject caches and distribution copies. If multiple valid checkouts remain or no source checkout exists, ask which path to use.
2. Read source `AGENTS.md` when present, `CLAUDE.md`, `base/rules/agents.md`, the provider's `rules/agents.md`, the catalog at `plugins/codex/itixo/scripts/model-catalog.json`, the generator, and the Codex installer. Invoke the provider's `dirigent` skill for repository mapping and any implementation, test, or documentation delegation. Keep the catalog as the model source of truth.
3. Before proposing or applying updates, present exactly two tables populated from the current source, not static examples:
   - **Level | Current model | Possible options**: include cheap, mid, security, and orchestrator for each provider in scope (identify the provider in the level cell). Resolve each current tier alias through `providers.<provider>.models` and `aliases.<alias>.providers.<provider>.default`; show the alias, concrete version, and configured effort. List every available non-pinned alias with that provider's `versions`, marking its default. Keep pinned selectors available for explicit compatibility requests. Show orchestrator as user-selected/inherit when its assignment is `inherit` or absent; do not invent a tier default or change the running session model.
   - **Agent name | Level**: include all eight canonical agents using the agent-to-tier mapping in `base/rules/agents.md`, including `itixo-planner` as orchestrator. Note any known explicit per-agent model or effort overrides beside the agent name; do not hide them behind a tier default.
4. Use a questionnaire tool when available; otherwise ask the same choices in text. Collect the provider and level to change, its alias, and the concrete version for each selected alias. Ask once per distinct provider/alias and reuse that version across its selected levels. Include keeping current values as an option. Ask separately about effort or per-agent overrides only when requested or needed for compatibility. Honor choices already supplied without asking again; never infer choices from a recommendation, alias name, or another provider. For a model not yet in the catalog, verify support before presenting it as an option. For a verify/check request, the tables remain read-only and no installation follows.
5. Preserve legacy selectors, existing custom choices, and unrelated provider entries. Treat `providers.<provider>.models` as tier-to-alias assignments and `aliases.<name>.providers.<provider>` as that provider's version catalog. A provider entry is the only availability signal; never infer support from an alias name or another provider. A request may independently change a provider's tier assignment (`cheap=luna` → `cheap=terra`) and/or that provider's alias `default` or `versions` entry (`sol` → `gpt-6-sol`); do not require both changes. Verify each requested model's exact provider ID and supported reasoning efforts against current official provider documentation and local runtime constraints. Ask only when tier, provider scope, or replacement policy is missing.
6. For a verify or check request, make no edits: report the proposed catalog diff or that no change is needed, plus validation evidence. For an update or promote request, edit the catalog in the source checkout, update defaults only within the authorized tier policy, regenerate with `node scripts/generate-agents.js`, and update affected user-facing docs, versions, and changelogs.
7. For an update, run `node scripts/generate-agents.js --check`, `node --test tests/*.test.js`, `node tests/validate.js`, and `node scripts/validate-plugin-changes.js --base <resolved-merge-base> --changelog-dir .`. Resolve `<resolved-merge-base>` from the current branch and `origin/HEAD`; report a missing or unusable base instead of weakening the check. Inspect `git diff` and `git status`.
8. For an update, commit each meaningful unit with `caveman:caveman-commit` or a terse Conventional Commit. Create or update a reviewable PR only when the user explicitly authorized publishing, using the configured GitHub connector or MCP first. Do not merge, release, or mutate external systems implicitly. Installation follows only the confirmed choices and scope below.

9. After confirmed Codex tier-model or version changes pass validation, invoke `itixo:install-agents` using `plugins/codex/itixo/skills/install-agents/SKILL.md` from the updated source checkout. Collect personal or project scope (and the project root) if not already supplied. Before replacement, read existing Itixo-managed files in that scope without editing them; show any model or effort differences from the pre-update defaults and ask which overrides to preserve when their intent is unknown. Pass the selected `--tier-model` and `--model-version` values, the selected cheap effort, and every confirmed `--agent-model` / `--agent-effort` override to the installer. Retain unchanged tier/version choices and explicit overrides, including planner overrides; model and effort precedence remain independent. Do not ask again for confirmed choices. Report installed/skipped paths and resolved values, and tell the user to start a new Codex task or restart Codex. If installation is blocked, report the blocker rather than claiming installed agents were updated.

After release, tell users to update the plugin through their provider's normal plugin flow. Claude and Copilot use their generated provider agents; do not run the Codex installer for their tier changes. Source verification alone never installs agents.
